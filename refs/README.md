## Why these are safe to commit

- **BepInEx** is open-source (MIT). Redistributing the DLLs is explicitly permitted.
- **Unity module DLLs** are Unity's official reference assemblies from NuGet, distributed under MIT. They declare the API surface but contain no game logic.
- **Cecil stubs** are our own minimal declarations of only the types/members the mod calls at compile time. They contain no game code — they're empty shells. At runtime, BepInEx loads the game's real assemblies and the mod's references resolve to the real types.

## How to use

The `HealthAutoArrange.Plugin.csproj` automatically falls back to `../refs` (this directory) when `GameDir` is not set via `HealthAutoArrange.Local.props` or the `HEALTHAUTOARRANGE_GAME_DIR` environment variable.

For full ABI verification against the real game, set `GameDir` to your actual game installation directory — the csproj will use the real `Assembly-CSharp.dll` and `UnityEngine*.dll` from `<GameDir>/CasualtiesUnknown_Data/Managed/` instead.

## Regenerating stubs

The Cecil stubs were generated by `/home/z/my-project/scripts/build_unity_stubs.cs` (not included in this repo). If the mod calls new game APIs or new Unity types, the stubs need updating. To regenerate:

1. Ensure the real Unity module DLLs (CoreModule, IMGUIModule, TextRenderingModule) are in `refs/CasualtiesUnknown_Data/Managed/`
2. Run the stub builder against those real modules
3. Commit the updated stubs

## CI / Release workflow

The release workflow (`.github/workflows/release.yml`) uses these committed refs by default — no GitHub Secret is required. If `GAME_REFS_URL` is configured as a secret, the workflow will download and use the real game references instead (for full ABI verification).
